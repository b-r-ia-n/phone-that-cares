TL;DR

The call

Ambitious version. Fork GrapheneOS (renamed, not claiming the GrapheneOS name), rewrite SystemUI for the real two-state lock-screen circle, build all four directions fully, pin to one Android version, no upstream merges for six months.

Real timeline: ~7–10 calendar weeks with 4–5 parallel Claude worktrees, ~13–17 weeks single-threaded. The single largest piece is Connect (~4 weeks) — not the OS work — because building a Matrix-bridge-backed inbox is itself a substantial product. Live test starts when the device boots stable, holds for 24 hours without intervention, and all four directions route correctly.

Three things this plan locks in that weren't locked before:

  • The lock screen is the lock screen. Thumbprint mid-screen authenticates, then a directional swipe completes unlock and routes into that mode. Two-state circle: static pre-auth (time / weather / notifications, same surface), interactive post-auth (the four-direction picker).
  • Ask is voice-IN only. No TTS. Whisper.cpp on-device as Plan A; fall back to Deepgram cloud if quality/latency fails. Response surface is the screen, not audio.
  • Connect runs on Matrix + bridges. Beeper's open-source mautrix ecosystem is healthy and actively maintained. We don't build messaging from scratch; we build a Compose UI on top of the Matrix Rust SDK.

The substrate choice

Fork GrapheneOS, rename it, pin to one Android version, sign with our own AVB key. Specifically not claiming to be GrapheneOS — the project is hostile to that for good reasons (brand protection, security-reputation concerns) and we don't need their endorsement.

Why GrapheneOS as substrate vs plain AOSP:

  • Better build system, Pixel device tree work done, vendor blob handling solved.
  • Their hardening work is free win even if not load-bearing.
  • If we ever revisit the banking question post-v1, the Sandboxed Play scaffolding is already there — we just can't use it in v1 (see banking tradeoff below).

Why not stay on stock GrapheneOS as overlay only:

  • You want the actual lock-screen replacement with the thumbprint-then-swipe-direction gesture. That requires owning SystemUI. That requires signing SystemUI with the platform key. On stock GrapheneOS we don't have that key.

Pin to one Android version. Pick the current stable GrapheneOS release at fork time. Don't merge anything for six months. The "AOSP maintenance treadmill" cost in the IMPOSSIBLE-D2 brief disappears entirely under this constraint — it was pricing in monthly Pixel patch tracking we're now skipping.

Banking — the real tradeoff

You can have the lock-screen replacement OR you can have Play-Integrity-passing banking. Not both in 2026.

GrapheneOS itself passes Play Integrity's device tier because Google whitelisted their specific AVB signing key. When we fork and sign with our own key, that whitelist doesn't transfer. We pass basic integrity (bootloader is locked with a valid key, signature chain intact) but not device integrity. Major US banks check device-tier or higher.

Apps that only check basic integrity still work. Some smaller banks, brokerages, and most utilities are fine. Specifically out: Venmo (which rejects Zygisk-class environments outright), Chase, Wells, Bank of America, Google Wallet, tap-to-pay. Some subset of these may surprise us either direction.

Practical handling: a second cheap phone for Venmo and any banking that fails. Physical card for tap-to-pay. This is the cost of the lock-screen replacement.

Feature set, v1

Built and shipped

  • Two-state lock-screen circle. Pre-auth: static, shows time / weather / notifications. Thumbprint mid-screen authenticates. Post-auth: interactive four-direction circle. 80px radius, 60px drag threshold to commit a direction. Color ramps from 33% to 85% of drag distance.
  • All four directions, all interactive. Discover (up), Ask (down), Connect (left), Home (right). Each goes to a real destination (next section).
  • Per-app gradual grayscale. Linear ramp from 0% to 100% saturation loss over the app's daily budget. SurfaceFlinger color matrix driven by a foreground-watcher service. Daily reset at midnight via AlarmManager. Ramp is feedback, not a limit — user can stay past the budget; the screen just becomes fully grayscale.
  • Per-app config UI. Sessions screen lets you set per-app mode (off / grayscale / etc.) and daily ramp minutes. Defaults: Instagram 30min grayscale, X 15min, others 20–45min off.
  • Passive tracking. UsageStatsManager ground truth, feeds the ramp progress + dashboard.
  • Argos integration. The val.town backend powers Ask's responses + the relationship memory layer that surfaces in Connect's About Person.

Deferred — explicitly

  • Feed blur, tweet-spacing, font-cycling, break-cards as treatments on external apps. The mock has these but applying them to other apps' rendering requires either accessibility-tree walking (fragile, breaks on app updates) or render-injection (genuinely hard). Defer to v2.
  • Banking apps that require device-integrity. Second phone. (See tradeoff above.)
  • Banking via Sandboxed Play. Scaffolding inherited but not configured for v1.
  • OTA infrastructure. You reflash by hand. ~10 minutes per update.

Build plan, phase by phase

Realistic totals: 13–17 weeks single-threaded, 7–10 weeks with 4–5 parallel worktrees. The 3× speedup factor (not 10×) reflects that hardware-iteration and OS-build debugging don't compress as well as code generation does.

P0

Tooling + OS substrate

Build server set up. Clone GrapheneOS at pinned tag, rename. Generate AVB signing keys. First boot on Pixel 6 with own key, bootloader relocked. adb-over-Tailscale wired. Watchdog supervisor + recovery flash script. Four worktrees with PROJECT_BRIEF.md.

1.5–2 wks
P1

SystemUI lock screen

Two-state circle. Fingerprint-authenticated transition from static to interactive. Drag physics: 80px radius, 60px commit threshold, ramped color feedback. Direction-to-activity routing. Keep stock unlock paths working (PIN fallback, SIM PIN, emergency dial — these classes get left alone).

2.5–3 wks
P2

Compose launcher shell + Home + Discover

Default-launcher claim. Home (4×4 + dock). Discover screen (Sessions in the mock): app tiles, progress bars, per-app mode + ramp-time config. Per-app state model wired to disk (Room or SharedPreferences). dayKey midnight reset via AlarmManager.

2–2.5 wks
P3

Per-app grayscale ramp

Foreground watcher service (Accessibility + UsageStats fallback). SurfaceFlinger color matrix driven via privileged binder service (we're now in our own fork, so this is clean — no Magisk-module hack). Linear interpolation from timeSpentTodayMs / (dailyRampMinutes × 60000). 250ms tick with visibility guards and >10s delta cap. Daily reset.

1.5–2 wks
P4

Ask voice-IN

Whisper.cpp build for Tensor G1. Compose UI: waveform, memory snippets, listening state. STT → Argos backend (val.town) → text response render. Memory writebacks. Fall-through to Deepgram cloud if Whisper quality/latency fails real-world test.

1.5–2 wks
P5

Connect via Matrix

Backend stood up (Beeper Plus account or self-hosted Synapse + bridges). Matrix Rust SDK integration in Compose. Unified inbox list. Conversation view. Think Out Loud reflection screen. About Person + relationship book (local, private — never proactive). Wire bridges in order: WhatsApp, iMessage (requires Mac running BlueBubbles or Beeper's bridge), Signal, Telegram, Google Messages. Instagram + Discord second wave.

3.5–4.5 wks
P6

Stabilization

Daily-driver dogfooding. Bug list from your own usage. No new features. Recovery-flash rehearsed end-to-end. Watchdog reports tuned.

1–1.5 wks
P7

Live test

Two weeks. SIM in the Pixel. Second phone for Venmo etc. Daily journal — one explicit question logged: "what did I open on the second phone today?" Mitigation for the developer-is-tester trap.

Multi-Claude orchestration

Five worktrees, at the upper end of the practical 4–8 concurrent ceiling per the loops research. File-ownership splits are clean.

os-systemui/
Opus. The SystemUI rewrite (P1) — most specialized, most asymmetric debugging. Java/Kotlin in the AOSP packages/SystemUI tree.
launcher-compose/
Sonnet. Home, Discover/Sessions, AboutPerson, ThinkOutLoud, ConversationScreen. P2 + P5-UI.
ask-voice/
Sonnet. Whisper.cpp build + Ask Compose UI + Argos backend wiring. P4.
connect-matrix/
Sonnet. Matrix Rust SDK integration, bridge configuration, inbox sync. P5-backend.
grayscale-service/
Sonnet. Foreground watcher, SurfaceFlinger binder, daily counter persistence. P3.

The harness lives separately (no resident Claude) — bash + Python + adb. Owns build, push, install, screenshot, logcat, cost cap, time cap, reboot-loop detection. Per the loops research, the supervisor owns cost / time / device safety; Claude owns code.

Goal-shaped checkpoints

Each phase has a /goal condition the Haiku judge can verify mechanically:

P1: keyguard_test.sh exits 0, fingerprint auth succeeds three times,
    drag-direction routing dispatches the correct intent on each side,
    no FATAL in logcat across three reboots. Stop after 40 turns.

P3: grayscale_ramp_test.sh exits 0, simulated 30-min Instagram session
    produces SurfaceFlinger matrix interpolation from 0 to 1 with
    monotonic progression, dayKey rollover at midnight resets to 0.
    Stop after 30 turns.

P5: matrix_bridge_test.sh exits 0, all five primary bridges (WhatsApp,
    iMessage, Signal, Telegram, Google Messages) report sync_complete,
    Connect inbox renders >= 3 conversations from each bridge.
    Stop after 50 turns.

Overnight runs use the Ralph Loop wrapper (fresh context per iteration, git-as-memory, autocommit). Watchdog must-haves still apply: token cap, wall-clock cap, command denylist, autocommit allowlist, no auto-flash without manual unlock.

Open questions

  1. Connect backend: Beeper Plus or self-host? Beeper Plus is $10/mo, fastest to working iMessage, well-supported. Self-host on Hetzner is $10/mo for the box, ~few days to stand up, more control + no third-party cap on accounts but you operate it. For v1 with you as tester, Beeper Plus is probably right; if Connect becomes the centerpiece for v2, self-host is the move. Confirm?
  2. iMessage requires a Mac running 24/7. Either a spare Mac mini you own (best), a paid VM with macOS (gray-area legally), or skip iMessage in v1. Beeper Plus includes their hosted Mac bridge but Apple has been fighting this — works currently. What's your Mac situation?
  3. Banking second phone. Cheap Android (you keep the Pixel 6's Sandboxed Play scaffolding for v2 if we ever revisit), or your previous phone? Won't affect the build, just the lifestyle plan during the test.
  4. Whisper.cpp Plan A really Plan A? Whisper.cpp small (~466MB) on Tensor G1 runs but latency varies. If first-token-to-text is >1s, the felt experience drops. Falling back to Deepgram cloud is a one-line change. Comfortable with the Plan A → fallback structure?
  5. Where do break-cards / blur / font-cycling etc. live? The mock has them. Real Android can apply them to our own rendered surfaces (Connect feed, eventually a Discover-built-in feed), but not to Instagram's. Defer entirely, or build them into our own surfaces so they're testable on Connect's inbox?
  6. Pixel 8a or 9 ordering. Pixel 6 EOL is Oct 2026. For a second tester later, we need newer hardware. Order during P0 so it's here, or wait?
