Executive summary

The headline call

Path B, scoped sharper than the original brief — with D2-overlay as the explicit v2 destination, not a v2 maybe.

Both adversarial pairs converged on the same insight from opposite sides: the four-direction "lock screen" should not be the lock screen. Treating it as "the first screen you see after unlock" removes the single most fragile piece of the stack (SystemUI hooking) and is honest about what stock Android lets you replace. POSSIBLE-D2 said it explicitly. IMPOSSIBLE-B said it as a cut. They're describing the same move.

Net effect: v1 ships in ~4 weeks of focused work with parallel Claudes, not 2 (POSSIBLE-B was optimistic) and not 6–10 (IMPOSSIBLE-B was correctly pricing in the SystemUI hook we're now cutting). The features that matter for the thesis test all survive. The features that mostly buy us "demo-pretty" got cut or deferred.

Per-app grayscale stays load-bearing. Passive tracking stays. Argos integration stays. The Compose launcher stays. The four-direction surface stays — just one swipe deeper than the lock screen. Banking is explicitly out-of-scope for v1 (second phone or a card). You're the v1 tester; we're treating that as a known-bias signal, not a license.

The v2 graduation path is the most interesting part: every line of code we write for v1 on Path B can move to D2-overlay (stock GrapheneOS substrate) unchanged, with the addition of a Sandboxed Play setup that restores banking. That graduation is what makes this a product trajectory and not a science experiment.

Build plan, phase by phase

Six phases. The first is tooling-only. The last is the live test. The four in the middle are the actual build. Total: ~7 calendar weeks if you're the only operator; ~4 if three Claudes are running parallel worktrees.

P0

Tooling & harness

Root the Pixel 6. Set up adb over Tailscale, watchdog supervisor, snapshot-and-restore script, the four worktrees with shared PROJECT_BRIEF.md. Get one trivial Magisk module flashing end-to-end from a Claude.

3–5 days
P1

Compose launcher + Argos backend

Home screen, sessions, ask, conversations, people, notifications shell. Argos calls the val.town endpoints. This is the biggest chunk and the most "normal Android app" of the lot. Sonnet on this worktree.

1.5–2 wks
P2

Per-app grayscale, foreground-gated

Phase A (fast win): AccessibilityService + WRITE_SECURE_SETTINGS route, the Grayscaler pattern. 2-second debounce for the flicker race. Phase B (polish if time): Magisk module that drives SurfaceFlinger color matrix directly, eliminating the flicker. Both worktrees can run in parallel.

1–1.5 wks
P3

First-screen-after-unlock surface

The four-direction picker as the launcher's primary screen. Connect direction wired up. The other three are visible-but-static. The launcher claims itself as default home; stock keyguard is untouched.

3–5 days
P4

Stabilization

Daily-driver dogfooding. Bug list from your own usage. No new features. Pixel monthly patch handling rehearsed (in case one lands during the live test). Recovery flash script tested end-to-end.

5–7 days
P5

Live test

Two weeks. SIM in the Pixel. Second phone for banking. Daily journal of what's working, what's annoying, what surprised you. The thesis test.

2 wks

Parallelization with multi-Claude

Four worktrees, three with a Claude resident, one passive (the harness):

launcher-compose/
Sonnet. Pure Kotlin/Compose. Owns P1, P3. Mostly device-independent inner loop (uses emulator MCP for fast iteration).
magisk-module/
Sonnet. Owns the SurfaceFlinger module half of P2. Needs the Pixel for verification.

Started as P3 worktree but reused for grayscale-via-accessibility-service. Sonnet.
device-harness/
No resident Claude. Bash + Python + adb. Owns build → push → install → screenshot → logcat. The supervisor that owns cost, time, device safety. Brian touches this directly.

The "decompose by file ownership not feature" rule (per the loops research) maps naturally here — each worktree owns disjoint files. They integrate at the APK level, not source.

The Claude Code loop stack

You asked specifically about /goal and how to use it. Short version: /goal is real, shipped May 12 (three days ago), and it's exactly the right primitive for an OS-modification project where success is measurable — boots, module loads, launcher renders. Here's the stack the research converged on.

The four named patterns

Auto Mode
Two-stage classifier that auto-approves routine tool calls within a turn. Removes prompt friction without giving up safety. Usually makes --dangerously-skip-permissions unnecessary.
/goal
Session-scoped completion condition (up to 4K chars). After each turn, a separate Haiku evaluator judges yes/no. "No" → another turn. "Yes" → done. The split between worker and judge is the whole point — LLMs are bad at deciding they're done; this fixes that. Works in headless -p mode for overnight runs.
Worktrees
Native since Feb 20. claude --worktree feature-x gives each Claude its own checkout. 4–8 concurrent is the practical ceiling; you bottleneck on review, not on Claude.
Ralph Loop
Community bash supervisor pattern (~100 lines). Runs Claude in fresh-context iterations against a progress.txt. Commits per iteration. State lives in git, not in the context window. The recipe for unattended overnight work.

What you want for the Android build

Use /goal for bounded "make this thing work" tasks where the completion condition is mechanically checkable — example:

/goal launcher renders on Pixel 6 boot, app_drawer.test.sh exits 0,
and adb logcat shows no FATAL across three consecutive reboots.
Stop after 40 turns.

The Haiku judge can verify this because the worker has to surface the test exit codes and logcat output in the transcript. Conditions like "the code is good" or "it feels right" do not work — there's nothing to read.

Use the Ralph Loop wrapper for overnight backlog grinding. Fresh context per iteration. Git-as-memory. A simple progress.txt like "fix all 12 launcher screen tests" gets ground through one task at a time, with the supervisor catching infinite loops and rate limits.

Use worktrees for the four-track parallelism in the plan above. Each Claude has its own checkout; merges happen at module boundaries.

Watchdog must-haves

This part is non-negotiable. The supervisor owns cost, time, and device safety; Claude owns code. Don't blur this.

  • Token-spend cap. Kill Claude at $X per worktree per night.
  • Wall-clock cap per /goal. 6 hours, then kill and email you.
  • Reboot-loop detector. If the Pixel has rebooted 5× in 10 minutes and not reached sys.boot_completed=1, halt and stage a fastboot-recovery flash — but do not auto-flash overnight. Require your manual unlock for any flash operation. This is the one place where unattended automation could brick the device while you sleep.
  • Command denylist. fastboot erase, fastboot flash, rm -rf, dd of=/dev/, writes outside the module's path. Only the supervisor flashes.
  • Per-iteration autocommit. Explicit git add allowlist. .gitignore for keys.
  • One-page HTML report per overnight run. Three screenshots (boot, launcher, after-module-load), logcat diff vs golden, the goal verdict and reason from Haiku, the token spend. You wake up to one glanceable artifact instead of a transcript.

Tether setup

ADB over Tailscale is the production pattern. USB-bootstrap once per reboot to enable adbd in TCP mode, then ADB-over-Tailscale-IP on port 5555. Never expose 5555 publicly — ADB has no authentication. Use Tailscale ACLs.

Cost realism

The $200 Max 20× plan is for individual experimentation, not for production orchestration. A four-worktree overnight run will find the bottom of that bucket. Plan on API billing for the overnight Opus passes; keep the daytime worktrees on Sonnet with Auto Mode. Drop MAX_THINKING_TOKENS for supervisor-driven loops where thinking isn't earning anything.

The adversarial collaboration, side-by-side

Four agents, two pairs. Each pair argued a specific candidate build. Each agent did real web research and cited concrete sources. The full briefs are in this folder; what follows is the boiled-down core of each argument plus my mediated read.

Pair 1 — Path B (rooted Pixel 6 + Magisk + LSPosed)

Possible

Doable in 2–3 weeks because every load-bearing component exists as a maintained open-source project. Magisk v30.7 ships Feb 2026. Vector (the LSPosed successor, 11.2k stars, v2.0 March 2026) is the live SystemUI-hooking framework. Per-app grayscale via SurfaceFlinger is a documented one-line shell command (service call SurfaceFlinger 1015). Pixel 6 is the most-trodden root target on the planet.

Strongest move

  • Cut banking from v1 entirely. Second phone for it. Deletes ~40% of engineering risk overnight.
  • Ship one of four lockscreen directions. The other three are static labels.
  • Reuse the Argos telegram backend unchanged.

Risks accepted

  • AccessibilityService can get killed by battery optimization. Mitigation: disable opt + foreground service.
  • LSPosed hook breaks a SystemUI subscreen we didn't test. Mitigation: defensive fall-through to original.
  • Two-week scope slips to four. Mitigation: ruthless cut list; week 3 is polish only.
Impossible

Slips to 6–10 weeks, with ~40% probability of quiet degradation. Four hostile maintenance treadmills — Play Integrity keybox revocations on a weekly cycle, monthly Pixel patches that have repeatedly broken root through 2025, SystemUI ABI churn forcing per-version branches, and the per-app foreground race — each have half-lives shorter than the time to build a feature on top of them.

Specifics that break

  • Revolut detects LSPosed itself (not just root). The moment you install the SystemUI hook, Revolut is gone.
  • Wells Fargo, Venmo, Chase, Crédit Mutuel, HSBC India, and many others reject Zygisk devices even with Shamiko.
  • Community grayscale tools (Grayscaler, GrayMan) document a flicker race requiring a 2-second debounce. Your "SurfaceFlinger Magisk" approach is novel, not well-trodden.
  • Sept 2025 Pixel patch broke Magisk root outright. People had to switch to KernelSU-Next.
  • Pixel 6 hits security-patch EOL in Oct 2026. ~17 months of life left.

The cut

  • Drop the SystemUI lockscreen hook from v1. Ship per-app grayscale as a normal Accessibility-service app. Argos as Compose launcher. Stock keyguard. 3–4 weeks, actually shippable.

Pair 2 — Path D2 (GrapheneOS substrate)

Possible

Build on GrapheneOS, not against it. Overlay first, fork only if overlay proves insufficient. Pixel 9 (not the 6), relocked bootloader with GrapheneOS's own AVB key, banking via Sandboxed Play Services. Costs ~2–3 extra weeks vs Path B; in exchange v1 is the same artifact as v2.

Strongest move

  • D2-overlay, not D2-fork. Forking is a maintenance treadmill and a political minefield.
  • Per-app grayscale via a privileged userspace service driving SurfaceFlinger's existing color-transform matrix.
  • Lock-screen overlay lives as launcher + post-unlock activity — not a SystemUI swap (which requires firmware signing keys you don't have on stock GrapheneOS anyway).
  • Sandboxed Play handles Chase, Amex, Vanguard, Discover, most UK banks per the 12-month report.

Risks accepted

  • Sandboxed Play coverage is per-bank. Check Brian's specific stack first.
  • SurfaceFlinger may not accept per-package transforms from userspace. Fallback: ~200-line patch to SurfaceFlinger.cpp — a thin fork, not the OS-fork project.
  • Pixel 6 EOL is Oct 2026. Budget Pixel 8a or 9 (~$500) for the second tester.
Impossible

Not "Path B plus banking" — a different category of project. You become an Android distribution maintainer. Realistic floor: 2–4 months to first daily-driver, with banking still partially broken, plus a permanent maintenance tax. The trap is that it's plausible enough to start and expensive in a slow-leaking way you don't notice until six months in.

Specifics that break

  • A forked GrapheneOS with its own AVB key does not pass meaningful Play Integrity. GrapheneOS itself passes only because Google whitelisted their key. Your fork has a different key, different attestation chain, no whitelist.
  • GrapheneOS's stance toward forkers is explicitly hostile (CalyxOS trademark/vendor-script denial). Don't expect help.
  • LineageOS, CalyxOS, /e/OS, DivestOS all need paid maintainers and still lag security patches. DivestOS shut down in 2025.
  • SystemUI is one of the most-churned AOSP components. Every release breaks your patch.
  • The "AOSP build server" reality: a first-time build is days, not hours. Real costs include OTA generation, signing pipeline, vendor blob extraction.

Honest concession

  • D2 is the right v2 if the v1 thesis lands. Don't make it v1.
  • Path B also fails Strong Integrity. The integrity difference is about which apps, not whether.

My mediated take

The convergence the agents didn't notice they made: POSSIBLE-D2 and IMPOSSIBLE-B independently concluded that the four-direction lockscreen should not literally replace the lock screen. POSSIBLE-D2 reframes it as "the first screen after unlock." IMPOSSIBLE-B says cut the SystemUI hook entirely. They are describing the same thing.

Once that's cut, Path B's hardest single subtask is gone. The IMPOSSIBLE-B 6–10 week estimate priced that in; without it, 4 weeks is realistic with parallel Claudes.

The deepest IMPOSSIBLE-D2 point isn't technical — it's displacement. If you spend 3–5 months on D2-fork, Argos doesn't get its per-app picker, the publishing bottleneck stays the bottleneck, and the thesis test gets delayed in service of also testing "can we relock the bootloader." That second question doesn't need an answer right now.

The deepest POSSIBLE-D2 point isn't technical either — it's the graduation argument. Path B's substrate is non-transferable by construction. A rooted Pixel is, by definition, a device only the developer can use. The DenyList cat-and-mouse is adversarial; social-app vendors and Google's Play Integrity team are actively shipping countermeasures. Any v1 → v2 transition on Path B starts with "throw out the substrate."

The synthesis: the work that's most transferable v1 → v2 is also the work that's most thesis-relevant. The launcher, the per-app grayscale logic, the foreground-watcher pattern, the Argos integration — all of it ports unchanged from Path B to D2-overlay. The work that doesn't port (LSPosed SystemUI hook, Magisk-specific module plumbing) is the work we're already cutting from v1.

So Path B-cut is mechanically the right v1, and D2-overlay is the explicit v2 destination — not a maybe. The graduation gate is "if the 2-week live test moves the needle, port to D2-overlay before adding a second tester."

Where the IMPOSSIBLE briefs were right and we're listening

  • Per-app grayscale needs the Accessibility-service mechanism first, not the SurfaceFlinger Magisk module. The community tools that already work do it the Accessibility way and document the 2-second debounce race. Build that first; the Magisk approach is a polish pass.
  • The four-direction lock screen is a v2 feature, not v1. Both sides effectively conceded this.
  • Banking is genuinely out, not "we'll try Shelter." Second phone. Honest scope.
  • "Developer as tester" hides breakage. The mitigation: keep a written daily journal during the live test, with a specific question — "what did I open on the second phone today?" If that number is >1 by day 3, the build's thesis is at risk and you should know.

Where the POSSIBLE briefs gave the actual recipe

  • Vector (LSPosed successor) is alive and maintained. The "LSPosed is archived" thing is misleading — the framework was forked and renamed. If we ever do the SystemUI hook in v2, this is the framework.
  • SurfaceFlinger color matrix from a Magisk module is well-trodden enough to use in P2 phase B, just not as the only mechanism.
  • D2-overlay is dramatically cheaper than D2-fork. The overlay-only D2 cost is "extra week of setup + Sandboxed Play config" — it's not the AOSP-maintainer category at all.
